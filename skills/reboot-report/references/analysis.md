## 数据完整性

- 把用户给出的本地时间窗规范为 `[开始, 结束)`，记录时区，再转换为 UTC
  查询。报告同时写本地时间和时区。
- 拉完所有分页后再分析。按事件 `id`、任务 `id` 去重，并记录 API 总量、
  拉取量、去重后数量和缺失页。
- 批次按 `created_at` 查询时，在时间窗两侧加入事件匹配容差，再用任务的
  实际时间筛回报告窗口，避免批次跨界造成漏数。
- 任务时间优先用 `pending_at`，缺失时依次用 `succeed_at`、`created_at`；
  报告或分析记录中注明最终使用的字段。
- 库存、机型和理论算力若来自当前快照，必须标明快照时间，不能伪装成历史
  时点数据。
- `listMiners` 的 `hashrate` 与 `expected_hashrate` 单位是 H/s；只有展示时
  才换算成 TH/s 或 PH/s。不要把原始值直接当成 TH/s。
- `getMinerStats.by_type` 的分类可重叠，不能相加；在线矿机数应使用
  `total - stale`。机型卡片优先使用
  `miner_model[].theoretical_hashrate`，并注明它来自当前快照。
- `listMiners.reboot_count` 与 `low_uptime_reboot_count` 是默认最近 7 天的
  聚合值。报告窗口不是同一个 7 天时，只把它们用于交叉检查，事实总量仍
  从 `listMinerRebootEvents` 按报告窗口计算。
- 当前运营标签使用 `tags`；`ops_status` 已废弃且固定为 null。
- 自动化批次若包含 `metadata.filterSummary`，可用 `total`、`passed` 与各
  `skipped...` 字段解释筛选瓶颈；手动批次没有该字段时不要补造。
- 所有比例都保存分子、分母；分母变化时分开展示，不混用“全部任务”、
  “已执行任务”、“已匹配任务”和“可评估任务”。

## 用语

| 对外用词       | 含义                                                  |
| -------------- | ----------------------------------------------------- |
| 检测到的重启   | `listMinerRebootEvents` 返回的场上观测事件            |
| Nonce 下发     | `miner.system.reboot` 任务；不等同于已经检测到重启    |
| Nonce 对齐重启 | 一个已执行任务与一个检测事件一对一匹配后的可归因样本  |
| 健康算力       | 默认 ≥ 80% 理论算力；若采用该默认值，必须在报告中写明 |
| 低算力         | \> 0 且低于健康算力                                   |
| 零算力         | ≈ 0                                                   |
| 反复重启       | 剔除电力相关窗口后，同机次数明显高于本场分布          |

Nonce 任务和检测事件是两套观测，不能直接相加，也不能默认前者是后者的
子集。只有“Nonce 对齐重启”才是检测事件中的可归因子集。封面分别写
“检测到的重启 / Nonce 下发 / 成功对齐”，并显示未匹配数量。

**文案语气**：用分析师白话，让非研发也能读懂。少用黑话、缩略词和网络词（如「爆量」「齐刷」「病灶」「画像」「误触」）。内部字段名（`hashrate_low`、uptime、batch）能换成白话就换；必须出现时先解释。

## 封面

三卡：机型与规模 / 数据范围 / 分析口径。只写基础上下文，不写分析推断。

- **机型与规模**：台数前 2～3 机型，每行 `N 台 · X TH`；其余「其他 · N 台」
- **数据范围**：起止、时长、时区；不写 Workspace；已确认场站计划可加一行
- **分析口径**：健康算力、检测事件数、Nonce 下发数、成功对齐数、
  Hashprice（或见收益页）

## 核心发现（3～4 条）

每条：`标题` + `一个主数字` + `一句带上下文的说明`。写比例、金额、谁触发；不写口径备注、不写内部字段名。

推荐四条骨架（按场况取舍）：

1. **重启构成** — 最大类型占比；可旁注 Nonce 对齐占比，及平静期与高峰期差异。
2. **Nonce 正向变化** — 主数字用日均产出能力或 run-rate，并明确这不是已实现收入。只基于成功对齐且数据完整的样本。
3. **健康机被重启** — 疑似电力集中事件里的健康机属场况扰动；若提 Nonce，须用成功对齐样本自己的健康占比。
4. **Nonce 下发与对齐** — 分别写下发、已执行、成功对齐和可评估数量。

## 事实页：先定义，再分布

### 定义页

检测总量 → Nonce 下发 → 成功对齐 → 检测结构（电力相关 / 高频 / 其他）。

- **检测到的重启**：场上观测总量
- **Nonce 下发**：平台创建的任务总量
- **Nonce 对齐重启**：可归因到平台任务的检测事件子集
- **电力相关 / 高频 / 其他**：对检测事件的互斥结构拆解

### 按日分布页

一天一行。主条（堆叠，互斥，合计 = 当日检测事件）：

1. **电力相关** — 短时大批量窗口（见下「疑似限电」）
2. **高频自重启** — 稳定期内同机次数明显高于本场分布；报告所用
   阈值及其依据
3. **其他** — 其余检测重启

同日下方贴蓝色细条：当日 **Nonce 对齐重启** 数，与主条同尺度。右侧写
`检测 X · 对齐 Y`。Nonce 下发数另列，不伪装成检测事件子集。

图例：三段占比 +“Nonce 对齐重启”全期次数。模板中每天复制一个
`.bar-row`；主条使用 `.bar-track`，蓝色细条使用 `.bar-nonce-track`。

可点出平静期与高峰期的对齐占比差异（若样本量足够且差异明显）。

建议加一页 **节奏对比**（平静期与高峰）：检测次数、Nonce 对齐占比、
关键小时桶；有机型偏差可旁注。

必要时增加 **疑似限电** 判断表。按固定时间桶分析并写明桶宽；10 分钟
可作默认起点，但不是未经验证的事实。判读列用 `疑似限电` / `偏限电` /
`不宜判限电`。

结构页优先对比 **全集与稳定期** 的重启前状态（健康占比被集中事件
抬高时很有用）。

效果可先给一页 **全集转移矩阵**作场况参照，再给 **Nonce 对齐样本**
的对象选择与正增量；勿把未对齐事件的健康→零算成 Nonce 失败。

建议页用模板 `.recommendations` > `.recommendation`（左问题 / 右方向），
不要用无样式的列表块。

### 运维专家视角（写发现时优先想这些）

1. **先分场况再谈策略**：若电力相关占比高，核心发现第一条应是限电抬高总量，而不是 Nonce 好坏。
2. **Nonce 与电力主窗口**：按任务执行时间核对 Nonce 是否落在疑似限电
   主窗口内。若主窗口内为 0、高峰下发集中在复电后时段，应明确写出，
   避免读者误以为平台在限电时同步重启矿机。
3. **机型偏差**：算「次/台」与反复重启占该机型比例；某一机型明显偏高时单独成条。
4. **Nonce 看对象选择 + 回升比例**：分母只用成功对齐且数据完整的样本；
   既报打在零算力的比例，也报零算力里算力明显回升的比例。
5. **建议标优先级**：P0 核对限电 / 现场清单 → P1 提高拉回 → 待确认另列。
6. **控制页数**：限电叙事不要拆成发现 + 节奏 + 限电表三页重复；节奏可并入按日分布副文案。全集转移矩阵可缩成效果页一句对照，不必单独成页。
7. **文案**：分析师白话；少黑话与网络词。

## 分类口径

### 疑似限电 / 电力相关

满足越多越稳（未与场站日志交叉验证时标「疑似」）：

- 短时段内很大比例矿机几乎同时出现检测重启
- 同时段全场算力先掉后回
- 大批 `pre_uptime` 高、`post_uptime` ≈ 0
- 大多对不上 Nonce 重启任务

健康占比高 → **疑似限电**；健康占比低、零算力为主 → **不宜判限电**（偏针对性批量）。未确认时不硬拆限电与断电。事实中保留；评估效果 / 收益时可剔除。

### 高频自重启

- 同机检测次数明显高于本场众数
- 常伴电力异常标记，通常无 Nonce 重启任务
- 对恰好覆盖最近 7 天的报告，可用 `reboot_count >= 10` 作为候选起点；
  其他窗口必须从检测事件重新计算
- `low_uptime_reboot_count / reboot_count > 50%` 只表示疑似反复启动，
  不是硬件故障定论

建议区分：维修候选（密集且运行时间短）与优化候选（反复零算力、
非硬件死循环）。事实保留；效果 / 收益可剔除。

### Nonce 任务与检测事件对齐

1. 仅把进入执行阶段的 `miner.system.reboot` 任务作为匹配候选；未执行任务
   仍计入“下发”，但不进入效果评估。
2. 候选必须是同一矿机，并落在明确记录的时间容差内。容差应依据检测采样
   间隔选择；没有依据时采用保守值并列为假设。
3. 多个候选时取时间最接近者。每个任务和事件最多使用一次，禁止重复匹配。
4. 分别报告任务未匹配数、事件未匹配数、匹配率和采用的任务时间字段。
5. 对不上就保留为未匹配，不用总量差额或相邻矿机补齐。

## 效果与收益（以对齐样本为主）

- 收益主叙事只看 **Nonce 对齐重启** 中数据完整的样本，不把未匹配检测
  事件算进平台策略成绩。
- 使用 `before_avg_hashrate` 与 `after_avg_hashrate`；缺任一值的样本不进入
  增量计算，但仍进入数据完整性说明。
- **正向增量**：仅对重启前为零/低算力且重启后回升的样本计算
  `max(after - before, 0)`，再从 H/s 转为 PH/s。
- 若没有回升持续时长，只能把“窗口内增量合计 ÷ 窗口天数 × 平均
  Hashprice”称为 **日均产出能力估算** 或 **日均 run-rate**，不能称为已经
  实现的收入。
- 若通过 `listMinerHistory` 得到回升持续时长，优先积分为 PH-day，再乘
  同期 Hashprice，作为有观察窗口支撑的收益估算。
- Hashprice 优先取 `listBtcNetworkHistory` 的窗口数据；采样不等间隔时做
  时间加权。来源、币种、单位和平均方式写入报告。
- 标成“/日”的数必须先按精确窗口小时数除以 24 换算天数。禁止把窗口
  合计 PH/s 直接乘 Hashprice 后标成每日收益。
- 可交代：零算力样本中出现正增量的比例（有效挽回率），避免只报瞄准率
- 健康机被 Nonce 打中的比例单独陈述；未对齐的疑似电力事件不要算进
  Nonce 失败
- 标「约」；不确定列入待确认

## 建议

策略方向与现场注意点即可。Automation 只谈触发规模与瓶颈方向，不写具体阈值。不确定列入「待确认」。
